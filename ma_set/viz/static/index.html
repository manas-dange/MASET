CHAPTER 01

Why IDEF0 Systems Engineering?

Most autonomous coding agents fail in production not because LLMs lack programming intelligence, but because unconstrained multi-agent loops collapse into chaotic feedback drift: repeating tool errors, generating hallucinated APIs, modifying out-of-scope files, or over-engineering simple bug fixes.

To solve this, MA-SET adopts the aerospace-grade IDEF0 (Integration Definition for Function Modeling) methodology. In IDEF0, every engineering activity is an invariant Function Block governed by four cardinal vectors (ICOM):

C • CONTROLS (Top)

Governing constraints that dictate how and when an agent may operate: Protected PathFilter policies (e.g. legacy_billing.py is strictly immutable), strict LLM budget ceilings (20 calls max), and mandatory Human-in-the-Loop impact sign-offs.

I • INPUTS (Left)

Artifacts transformed by the function: Requirements tickets (YAML/GitHub), raw source repository snapshots, pytest failure stack traces, and code reviewer critiques.

O • OUTPUTS (Right)

Deliverables synthesized by the function: Decomposed execution specs, clean git patch diffs, automated pull requests with release notes, and append-only JSONL telemetry trails.

M • MECHANISMS (Bottom)

The executors supporting the function: Frontier LLM adapters (Claude 3.5 Sonnet, GPT-4o, Gemini 1.5 Pro), disposable sandboxed git environments, AST parsers, and the LangGraph Pregel state graph.

CHAPTER 02

The Orchestration Core: LangGraph Pregel Graph

MA-SET is implemented as a cyclic directed state graph using LangGraph's Pregel execution framework. Unlike linear chain-of-thought, MA-SET persists an immutable state record across seven specialized agent nodes:

  • Node A1 (Planner): Evaluates tickets, extracts acceptance criteria, checks priority, and decomposes complex feature requests into atomic engineering milestones.
  • Node A2 (Architect): Analyzes repository dependency graphs, detects potential side-effects, and generates precise architectural specs.
  • Gate 1 (Human-in-the-Loop Gate): Asynchronous governance checkpoint where engineers can approve, reject, or inject modifications before developer agents execute arbitrary file mutations.
  • Node A3 (Developer): Operates strictly within an isolated sandbox to write code, patch regressions, and implement features according to spec.
  • Node A4.1 (Tester): Executes automated pytest suites in disposable environments, capturing real exit codes and traceback telemetry.
  • Node A4.2 (Reviewer): Audits code quality, style guidelines, and AST structure. Rejects overengineered or insecure solutions.
  • Gate 2 (Zero-Defect Regression Gate): Hard automated barrier. If any pre-existing unit test breaks, the pipeline rejects the patch immediately.
  • Node A5 (DevOps): Commits verified patches to isolated branches, authors pull requests with release notes, and reports completion.
CHAPTER 03

Disposable Git Sandbox & PathFilter Containment

Security and environmental purity are paramount. Every agent run executes in an ephemeral, disposable workspace initialized on-the-fly: 

# Sandbox Lifecycle Guarantee:
1. Temporary directory created (/tmp/maset_sandbox_xyz)
2. Target project cloned without .git pollution
3. Fresh git repository initialized (git init, git add, git commit -m "Baseline")
4. PathFilter active: Intercepts all file mutations against protected invariants
5. Ephemeral workspace automatically cleaned up on exit

Any attempt by an LLM to modify protected files (such as legacy_billing.py, .env, or root security configs) is immediately intercepted by the PathFilter before touching disk, logging an immutable FILE_WRITE_BLOCKED audit event.

CHAPTER 04

Dual-Loop Self-Healing: FB1 & FB2 Recovery Dynamics

Frontier models frequently write code with subtle syntax slips or off-by-one errors on their initial pass. MA-SET utilizes a dual-nested feedback loop architecture to automatically recover without human intervention:

FB1: Developer ↔ Tester Loop

When pytest fails, the Tester extracts the failing assertion and traceback, feeding it directly back to the Developer. The Developer enters a RECOVERY_STARTED episode, analyzes the error, and iterates (capped at 3 retries) until the test suite passes.

FB2: Reviewer ↔ Developer Loop

Even if tests pass, the Reviewer inspects AST diffs for code bloat, security antipatterns, or style regressions. If rejected, constructive feedback triggers an architectural refinement loop back to the Developer.
